# Evaluation

## Definition

Evaluation은 생성된 결과가 좋은지 판정할 기준과 방법을 미리 정하는 원리다.
성공 기준(무엇이 맞는가)과 평가 케이스(실제로 맞는지 확인하는 시험)를 포함한다.

---

## Why

기준 없이 프롬프트를 고치면 "길어졌다"와 "좋아졌다"를 구분할 수 없다.
공식 가이드들은 프롬프트를 고치기 전에 먼저 성공 기준과 평가 방법을 정하고,
수정 전후를 같은 기준으로 비교하라고 강조한다.

---

## When to use

- 프롬프트를 개선·비교해야 할 때 (수정 전후 비교)
- 결과 품질을 반복적으로 관리해야 하는 실제 서비스
- 여러 프롬프트 후보 중 더 나은 것을 골라야 할 때

---

## When NOT to use

- 일회성·즉흥적 질문이라 품질을 관리할 필요가 없을 때
- 다만 실제 서비스나 포트폴리오라면 Evaluation을 생략하지 않는 것이 원칙이다.

---

## Good Example

```
성공 기준:
- 음식점과 무관한 질문은 off_topic으로 분류한다.
- 예약 요청은 reservation으로 분류한다.

평가 케이스:
입력 "오늘 날씨 알려줘"        -> 기대: off_topic
입력 "내일 저녁 7시 예약해줘"  -> 기대: reservation

프롬프트 수정 후, 위 케이스를 다시 실행해 결과가 나아졌는지 비교한다.
```

무엇이 성공인지, 어떻게 측정하는지가 분명하고 수정 전후 비교가 가능하다.

---

## Bad Example

```
그냥 결과가 좋아 보이면 됐어.
(프롬프트를 계속 길게 고치면서 매번 눈대중으로 판단)
```

왜 나쁜가:
- "좋아 보인다"는 측정 불가능해 개선 여부를 알 수 없다.
- 같은 기준으로 비교하지 않아, 한 곳을 고치다 다른 곳이 나빠진 것을 놓친다.

---

## Common Mistakes

- 성공 기준을 "좋은 답변"처럼 측정 불가능하게 적는다.
- 평가 케이스 없이 프롬프트 문장만 계속 고친다.
- 수정 후 같은 케이스로 다시 검증하지 않아 개선 여부를 확인하지 못한다.

---

## Checklist

- [ ] 성공 기준을 관찰·판정 가능한 조건으로 적었는가? (예/아니오)
- [ ] 성공을 확인할 평가 케이스(입력-기대결과)가 있는가?
- [ ] 프롬프트 수정 후 같은 케이스로 다시 검증하는가?
- [ ] 수정 전후를 같은 기준으로 비교하는가?
